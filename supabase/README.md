- `tests/rls_check.sql`: acts as a visitor, a guest and a venue owner to check the security rules, then removes its test data. Run it in the SQL editor after any change to the rules.
- `seed.sql`: the 11 example venues from the demo, with rooms, extras and reviews. Generated by `node scripts/make-seed.mjs`. Every row is marked `is_demo`, so it can be cleared before launch with `delete from public.venues where is_demo;`.

## Tables

| Table | What it holds |
|---|---|
| `profiles` | Guests and venue owners (one per login) |
| `venues` | Listings: details, good-to-know, cancellation policy, prices by day |
| `rooms`, `addons` | Each venue's spaces and extras, with prices in pence |
| `availability_blocks` | Phone and in-person bookings, and closed dates, added by the venue |
| `bookings`, `booking_addons` | Bookings made on Vendo, with the price breakdown and payment plan |
| `messages` | Conversations between a guest and a venue |
| `venue_reviews`, `guest_ratings` | Reviews both ways |
| `saved_venues`, `waitlist` | Hearts and waiting lists |
| `payouts` | Money paid out to venues |

## Security

Row level security is on for every table:

- Anyone can see live venues, their rooms, extras and reviews.
- Only the venue sees its own availability details. The public calendar uses `venue_busy_days()`, which returns dates only.
- Guests see their own bookings, messages, saved venues and waiting lists. Venues see bookings and messages for their own venues.
- Only an admin can put a venue live for the first time, or give someone admin access.
- Payouts are written only by the server.
