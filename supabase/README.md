The migration and seed below have been run on it, and `tests/rls_check.sql` passes (19 checks).

- `migrations/20261116000000_init.sql`: the tables, security rules and helper functions.
- `migrations/20261116130000_account_types.sql`: adds the account type (guest or venue owner), venue name and type, when the terms were accepted and the marketing opt-in to profiles, filled in from the sign-up form.
- `tests/rls_check.sql`: acts as a visitor, a guest and a venue owner to check the security rules, then removes its test data. Run it in the SQL editor after any change to the rules.
- `seed.sql`: the 11 example venues from the demo, with rooms, extras and reviews. Generated by `node scripts/make-seed.mjs`. Every row is marked `is_demo`, so it can be cleared before launch with `delete from public.venues where is_demo;`.

## Tables

| Table | What it holds |
|---|---|
| `profiles` | Guests and venue owners (one per login) |
| `venues` | Listings: details, good-to-know, cancellation policy, prices by day |
| `rooms`, `addons` | Each venue's spaces and extras, with prices in pence |
| `availability_blocks` | Phone and in-person bookings, and closed dates, added by the venue |
| `bookings`, `booking_addons` | Bookings made on Vendo, with the price breakdown and payment plan |
| `messages` | Conversations between a guest and a venue |
| `venue_reviews`, `guest_ratings` | Reviews both ways |
| `saved_venues`, `waitlist` | Hearts and waiting lists |
| `payouts` | Money paid out to venues |

## Security

Row level security is on for every table:

- Anyone can see live venues, their rooms, extras and reviews.
- Only the venue sees its own availability details. The public calendar uses `venue_busy_days()`, which returns dates only.
- Guests see their own bookings, messages, saved venues and waiting lists. Venues see bookings and messages for their own venues.
- Only an admin can put a venue live for the first time, or give someone admin access.
- Payouts are written only by the server.

## Admin

- `migrations/20261116150000_admin.sql`: the admin email list (`admin_emails`), automatic admin access for listed emails when they sign up, running costs (`admin_costs`) and `admin_stats()`, which returns every dashboard figure and refuses anyone who isn't an admin.
- `tests/admin_check.sql`: proves a listed email becomes admin, a normal user can't read the stats or costs or make themselves admin, and an admin can. 10 checks, all passing.
- To add an admin, run in the SQL editor: `insert into public.admin_emails (email) values ('name@example.com');` If they already have an account, also run: `update public.profiles set is_admin = true where id = (select id from auth.users where email = 'name@example.com');`

## Venue verification

- `migrations/20261116170000_venue_verification.sql`: venue owners add a venue (draft, then "pending review"), with photos in the public `venue-photos` bucket and their ID, premises licence and insurance certificate in the private `venue-docs` bucket. Files sit in a folder named after the venue, and only that venue's owner and admins can open the documents.
  - `venue_docs`: what the owner tells us (legal name, licence number and council, insurer, cover, expiry) and where their files are. Owner and admins only.
  - `venue_checks`: the admin's three checks (ID, licence, insurance) and notes. Admins only.
  - `venues.verified`: the "Verified venue" badge. Only `approve_venue()` sets it, and only once all three checks are ticked. Unticking a check removes it straight away.
  - `send_back_venue()` returns a venue to draft with a note the owner sees.
  - Owners can't verify their own venue, put it live, mark it as a demo or edit the admin's note.
- `tests/venue_check.sql`: 28 checks covering owners, another owner, signed-out visitors and an admin, including file access. All passing.
